# CyberShield — نطاق المشروع

**الإصدار:** 1.1
**النطاق:** Project 1 — Website Security Assessment
**المنصة المستهدفة:** Android
**لغة الواجهة:** العربية مع دعم RTL
**الخادم:** Python وFlask
**حالة الوثيقة:** نطاق التنفيذ الأولي

## 1. تعريف المشروع

CyberShield هو تطبيق موبايل يوفر تقييمًا أوليًا ومحدودًا لبعض
مؤشرات أمان المواقع الإلكترونية المصرح بفحصها.

يتكون النظام من تطبيق Flutter، وخادم API باستخدام Flask،
ومحرك فحص مكتوب بلغة Python يستخدم Requests للاتصال بالمواقع
وجمع الأدلة اللازمة لإنتاج تقرير منظم.

يعرض التطبيق نتيجة كل فحص وتفسيرها والتوصيات والقيود المرتبطة بها.

لا يمثل CyberShield اختبار اختراق شاملًا، ولا يضمن أمان الموقع
بالكامل، بل يقيّم مجموعة محددة من المؤشرات في استجابة معينة
وفي وقت إجراء الفحص.

## 2. المشكلة التي يعالجها المشروع

قد لا يعرف أصحاب المواقع والمطورون ما إذا كان موقعهم يستخدم
اتصال HTTPS قابلًا للتحقق، أو يرسل بعض ترويسات الحماية الأساسية.

يسعى CyberShield إلى عرض نتائج هذه الفحوصات بلغة واضحة،
مع توضيح الأدلة والملاحظات والتوصيات المناسبة.

## 3. أهداف المشروع

- توفير واجهة موبايل بسيطة باللغة العربية مع دعم RTL.
- السماح بإدخال رابط الموقع والتحقق من صيغته.
- طلب تأكيد أن المستخدم يملك تصريحًا مناسبًا للفحص.
- تطبيق سياسة الهدف في الخادم قبل الاتصال.
- التحقق من اتصال HTTPS وشهادة TLS.
- فحص أربع ترويسات حماية محددة.
- توحيد النتائج ضمن نموذج بيانات معروف.
- إعادة تقرير منظم بصيغة JSON عبر Flask API.
- معالجة أخطاء الاتصال والمدخلات بصورة مفهومة.
- توفير اختبارات آلية وتوثيق واضح للتشغيل.
- منع الادعاءات التي تتجاوز الأدلة المتاحة.

## 4. الفحوصات ضمن Project 1

تتكون النسخة الأساسية من خمسة فحوصات.

### 4.1 اتصال HTTPS والتحقق من TLS

معرّف الفحص: `https_connection`

يتحقق من إمكانية الاتصال بالموقع عبر HTTPS مع إبقاء التحقق
من شهادة TLS واسم المضيف مطلوبًا.

يجب تصنيف أخطاء الاتصال والشهادة وDNS والمهلة بحسب الأدلة
المتاحة، وعدم اعتبار الاتصال ناجحًا إذا فشل التحقق من الشهادة.

اجتياز هذا الفحص لا يعني أن الموقع خالٍ من الثغرات.

### 4.2 ترويسة HSTS

معرّف الفحص: `header_hsts`

الترويسة: `Strict-Transport-Security`

يتحقق الفحص الحالي من وجود الترويسة ومن أن قيمة `max-age`
عدد صحيح موجب.

لا يثبت هذا الفحص أن جميع إعدادات HSTS مناسبة للموقع،
ولا يشترط تلقائيًا تفعيل جميع الخيارات الإضافية.

### 4.3 ترويسة CSP

معرّف الفحص: `header_csp`

الترويسة: `Content-Security-Policy`

يتحقق الفحص الحالي من وجود سياسة CSP المفروضة في الاستجابة.

لا يحلل الإصدار الحالي جودة جميع التوجيهات أو يثبت أن السياسة
فعالة ضد جميع أنواع الهجمات.

ترويسة `Content-Security-Policy-Report-Only` لا تعادل سياسة
مفروضة؛ يجب أن تميز المعالجة المستقبلية بينهما بوضوح.

### 4.4 ترويسة X-Content-Type-Options

معرّف الفحص: `header_x_content_type_options`

الترويسة: `X-Content-Type-Options`

يتحقق الفحص من وجود القيمة `nosniff`.

وجود هذه القيمة لا يثبت الحماية من جميع أنواع الهجمات.

### 4.5 ترويسة X-Frame-Options

معرّف الفحص: `header_x_frame_options`

الترويسة: `X-Frame-Options`

يتحقق الفحص الحالي من القيمة `DENY` أو `SAMEORIGIN`.

يجب تفسير غياب الترويسة في سياقها، مع مراعاة أن سياسة
CSP التي تستخدم `frame-ancestors` قد توفر حماية ذات صلة.

غياب الترويسة وحده لا يثبت وجود ثغرة مؤكدة.

## 5. حالات النتائج

تستخدم الفحوصات الحالات التالية:

- `passed`: اجتاز الفحص المحدد قاعدته الموثقة.
- `warning`: توجد ملاحظة تستحق المراجعة.
- `not_verified`: الأدلة غير كافية للتحقق.
- `error`: حدث خطأ أثناء تنفيذ الفحص أو معالجة الاستجابة.
- `skipped`: لم ينفذ الفحص بسبب قيد محدد وموثق.

يجب ألا تتحول نتيجة غير حاسمة إلى `passed`.

كما يجب عدم اعتبار تعذر الاتصال دليلًا على أن الترويسات مفقودة؛
بل تسجل هذه الترويسات على أنها غير قابلة للتحقق.

## 6. نموذج النتيجة

يحتوي كل فحص على الحقول التالية:

- `check_id`
- `title`
- `status`
- `severity`
- `confidence`
- `evidence`
- `explanation`
- `recommendation`
- `limitations`

قيم الخطورة المعتمدة:

- `info`
- `low`
- `medium`
- `high`

قيم الثقة المعتمدة:

- `low`
- `medium`
- `high`

يحتوي التقرير أيضًا على معلومات الفحص والوقت وإصدار المحرك
وملخص النتائج والقيود العامة.

يجب توثيق أي تغيير في نموذج التقرير ومراجعته مع مسؤولي
Flask وFlutter قبل اعتماده.

## 7. التقنيات المعتمدة

- Flutter وDart: تطبيق الموبايل.
- Python: الخادم ومحرك الفحص.
- Flask: واجهة API.
- Requests: الاتصال بالمواقع.
- JSON: تبادل البيانات.
- pytest: اختبارات Python.
- Git: إدارة الإصدارات.
- لا توجد قاعدة بيانات مطلوبة في النسخة الأساسية.

يجب تسجيل إصدارات الاعتماديات التي اختبرها الفريق فعلًا
ضمن ملف الاعتماديات المتفق عليه.

## 8. واجهة API

توفر النسخة الأولية مسارين أساسيين:

- `GET /api/v1/health`: التحقق من استجابة API.
- `POST /api/v1/scan`: طلب فحص وإرجاع التقرير.

طلب الفحص يتضمن:

- `target_url`: رابط الموقع.
- `authorization_confirmed`: تأكيد المستخدم أنه يملك تصريحًا مناسبًا.

تتحقق الواجهة الخلفية من الطلب وسياسة الهدف بصورة مستقلة.
ولا يعتبر تأكيد المستخدم وحده كافيًا للسماح بالاتصال.

عقد API الحالي مسودة، ويجب اعتماده بالتنسيق بين دلال وبيلسان وأحمد.

## 9. حدود المشروع

لا تتضمن النسخة الأولى:

- تخمين كلمات المرور أو محاولات تسجيل الدخول.
- فحص MFA أو إدارة الجلسات.
- تحليل مستقل لخصائص Cookies.
- اكتشاف جميع ثغرات الويب.
- اختبار اختراق هجومي شامل.
- الزحف إلى الصفحات أو النطاقات الفرعية.
- نظام حسابات متكامل للمستخدمين.
- قاعدة بيانات أو سجل دائم للتقارير.
- المراقبة الدورية أو مقارنة التقارير بمرور الزمن.
- نظام مهام موزع.
- تقارير PDF متقدمة.

يمكن تقييم الإضافات المستقبلية بعد إكمال النطاق الأساسي واختباره.

## 10. سياسة أمن الهدف والاتصال

يجب أن يطبق الخادم سياسة هدف مستقلة قبل الاتصال.

تتضمن المتطلبات:

- السماح بـ HTTPS فقط في النسخة الأولية.
- السماح بالمنفذ القياسي 443 فقط.
- رفض الروابط غير الصالحة والمعلومات المضمنة للاعتماد.
- رفض localhost وعناوين الشبكات الخاصة والمحظورة.
- معالجة IPv4 وIPv6 وفق السياسة.
- رفض أهداف DNS التي تحتوي على عناوين غير مسموحة.
- تعطيل اتباع التحويلات تلقائيًا.
- إبقاء التحقق من شهادة TLS واسم المضيف مطلوبًا.
- فرض مهلات زمنية وحدود مناسبة للموارد.
- عدم كشف بيانات حساسة أو تفاصيل داخلية في رسائل الأخطاء.
- عدم تسجيل معلومات اعتماد أو رموز جلسات أو بيانات غير لازمة.

يجب التحقق من أن الاتصال الفعلي يستخدم عنوان IP الذي اجتاز
سياسة الهدف، دون تجاوز التحقق من اسم المضيف وشهادة TLS.

نجاح الاختبارات الحالية لا يثبت وحده اكتمال حماية SSRF.
يجب إكمال اختبارات الاتصال الفعلي وحالات DNS وTLS قبل اعتبار
الماسح جاهزًا للنشر أو للاستخدام العام.

## 11. حدود النتائج

تعتمد النتائج على الاستجابة التي استطاع محرك الفحص الوصول إليها.

قد تختلف الترويسات حسب المسار أو إعدادات الخادم أو الشبكات
الوسيطة أو حالة المستخدم.

لا يجوز أن يعرض التطبيق عبارة «الموقع آمن بالكامل».

يجب توضيح أن التقرير تقييم أولي محدود، وأن وجود ترويسة
لا يثبت سلامة إعدادها بالكامل، وأن غياب ترويسة لا يعني
بالضرورة وجود اختراق مؤكد.

## 12. معيار القبول

تعتبر النسخة الأساسية مستوفية للوظائف المحددة عندما:

- يمكن للمستخدم إدخال رابط صالح ومصرح به.
- يرفض الخادم المدخلات والأهداف المحظورة.
- يعمل فحص HTTPS وTLS وفق قواعد موثقة.
- تعمل فحوصات الترويسات الأربع وفق القواعد المحددة.
- ينتج الخادم تقرير JSON متوافقًا مع عقد API المعتمد.
- يحتوي التقرير على الأدلة والتفسيرات والتوصيات والقيود.
- تعالج الأخطاء دون إظهار معلومات داخلية حساسة.
- تنجح الاختبارات المتفق عليها للفحوصات وAPI.
- يستطيع Flutter عرض التقرير والأخطاء باللغة العربية.
- تكون قيود الفحص ظاهرة للمستخدم.

لا يكتمل القبول الأمني بمجرد نجاح الاختبارات الوظيفية؛
يجب أيضًا مراجعة سياسة الهدف والتحقق من سلوك الاتصال الفعلي
واستكمال الاختبارات الأمنية المطلوبة.
