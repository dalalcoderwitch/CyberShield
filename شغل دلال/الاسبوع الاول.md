# تقرير إنجازات دلال – الأسبوع الأول من مشروع CyberShield

## 1. الهدف الأساسي من الأسبوع الأول

كان الهدف خلال الأسبوع الأول هو تأسيس الجزء الخاص بي من المشروع، وتجهيز البنية الأولية للـ Backend والـ Security Scanner، وتحديد طريقة عمل الفحوصات الأمنية وشكل النتائج التي سيستقبلها تطبيق Flutter لاحقًا.

لم يكن الهدف في هذا الأسبوع بناء ماسح أمني متكامل أو تنفيذ جميع الفحوصات على مواقع حقيقية، بل وضع أساس تقني واضح ومنظم يسمح للفريق بالانتقال إلى التنفيذ والتكامل في المراحل التالية.

## 2. تحديد التقنيات المعتمدة في المشروع

تم تثبيت الاختيارات التقنية الأساسية التي سنعتمد عليها في النسخة الأولى:

| الجزء | التقنية |
|---|---|
| تطبيق الهاتف | Flutter + Dart |
| الخادم الخلفي | Python + Flask |
| إرسال طلبات المواقع | Requests |
| تبادل البيانات | JSON |
| اختبارات Python | pytest |
| قاعدة البيانات | لا توجد في الإصدار الأول |

وتم الاتفاق على استخدام **Flask بدل FastAPI** في النسخة الأولى، وعدم إدخال قاعدة بيانات في هذه المرحلة حتى يبقى نطاق المشروع محدودًا وواضحًا.

كذلك تم اعتماد اللغة العربية في التطبيق مع دعم اتجاه الكتابة من اليمين إلى اليسار RTL.

## 3. تحديد نطاق الفحوصات الأمنية للإصدار الأول

عملت على تحديد الفحوصات التي سيقوم بها CyberShield، حتى لا يتوسع المشروع إلى اختبارات كثيرة يصعب تنفيذها وتأمينها خلال النسخة الأولى.

تم اعتماد خمسة فحوصات أساسية:

1. **HTTPS Connection – `https_connection`**
   - التحقق من إمكانية الاتصال بالموقع عبر HTTPS.
   - التحقق من شهادة TLS.
   - إبقاء التحقق من الشهادة مفعّلًا، وعدم تجاوز أخطاء الشهادات.

2. **HSTS – `header_hsts`**
   - فحص وجود ترويسة `Strict-Transport-Security`.
   - تجهيز طريقة تقييم القيمة التي تحتويها الترويسة.

3. **Content Security Policy – `header_csp`**
   - فحص وجود ترويسة `Content-Security-Policy`.
   - تحديد أن وجود الترويسة وحده لا يكفي للحكم على جودة السياسة الأمنية.

4. **X-Content-Type-Options – `header_x_content_type_options`**
   - فحص الترويسة.
   - اعتماد القيمة `nosniff` باعتبارها القيمة المطلوبة للفحص المحدد.

5. **X-Frame-Options – `header_x_frame_options`**
   - فحص الترويسة.
   - التعامل مع القيمتين `DENY` و`SAMEORIGIN` باعتبارهما القيمتين المقبولتين لهذا الفحص.

كما تم تحديد الأمور التي لن تدخل ضمن الإصدار الأول، ومنها:
- فحص كلمات المرور.
- اختبار تسجيل الدخول.
- فحص المصادقة متعددة العوامل MFA.
- فحص إدارة الجلسات.
- محاولات التخمين أو Brute Force.
- حفظ سجل الفحوصات في قاعدة بيانات.

كان هذا التحديد مهمًا حتى يبقى المشروع قابلًا للتنفيذ والاختبار، ولا يعطي المستخدم انطباعًا بأن التطبيق ينفذ فحصًا أمنيًا شاملًا للموقع.

## 4. تأسيس البنية الأولية للـ Backend

بدأت العمل على الأساس البرمجي الذي سيستقبل طلبات تطبيق Flutter ويجهزها للماسح الأمني.

تم اعتماد Flask ليكون مسؤولًا عن استقبال الطلبات وإدارتها، مع تحديد مسارات API الأساسية:

### أولًا: Health Endpoint

`GET /api/v1/health`

وظيفته التأكد من أن خدمة CyberShield API تعمل.

تم تحديد شكل الاستجابة المتوقع:

```json
{
  "status": "ok",
  "service": "CyberShield API"
}
```

### ثانيًا: Scan Endpoint

`POST /api/v1/scan`

هذا المسار مخصص لاستقبال طلب فحص موقع من تطبيق الهاتف.

تم تحديد شكل الطلب المتفق عليه:

```json
{
  "target_url": "https://example.com",
  "authorization_confirmed": true
}
```

ويحتوي الطلب على:
- `target_url`: عنوان الموقع المطلوب فحصه.
- `authorization_confirmed`: تأكيد المستخدم أنه يملك الموقع أو لديه تصريح صريح لفحصه.

الهدف من هذه الخطوة كان توحيد طريقة التواصل بين التطبيق والخادم، حتى يعرف أحمد وبيلسان شكل البيانات التي يجب إرسالها واستقبالها.

## 5. وضع قواعد التحقق من طلب الفحص

تم تحديد قواعد أساسية يجب أن يلتزم بها الـ Backend قبل تمرير الطلب إلى الماسح الأمني، ومنها:

- التأكد من أن الطلب يحتوي على البيانات المطلوبة.
- التأكد من أن عنوان الموقع نص صالح.
- التأكد من أن المستخدم أكد امتلاكه الموقع أو امتلاكه تصريحًا بفحصه.
- عدم السماح ببدء الفحص إذا لم يتم تأكيد التفويض.
- عدم اعتبار أي عنوان يرسله التطبيق آمنًا تلقائيًا.
- تجهيز استجابات واضحة للطلبات غير الصالحة أو غير المسموح بها.

كما تم اعتماد شكل موحد للأخطاء، مثل:

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "بيانات الطلب غير صالحة."
  }
}
```

وهذا يساعد تطبيق Flutter على فهم سبب فشل الطلب وعرض رسالة مناسبة للمستخدم بدل استقبال أخطاء غير واضحة.

## 6. تأسيس فكرة الماسح الأمني Scanner

تم العمل على تحديد الفصل بين مسؤوليات الـ API ومسؤوليات الماسح الأمني.

الفكرة المعتمدة هي:

- Flask يستقبل الطلب ويتحقق منه.
- بعد اجتياز التحقق، يستدعي الماسح الأمني.
- الماسح ينفذ الفحوصات المحددة.
- الماسح يعيد النتائج بصيغة منظمة.
- الخادم يجهز الاستجابة النهائية ويرسلها إلى تطبيق الهاتف.

وتم تحديد واجهة العمل المقترحة للماسح:

```python
scan_target(target_url: str) -> dict
```

هذه الواجهة تجعل ربط الماسح مع Flask أوضح، وتسمح بتطوير الفحوصات الداخلية دون الحاجة إلى تغيير طريقة تعامل التطبيق مع الـ API في كل مرة.

كما تم تجهيز الهيكل الأولي للعمل على الفحوصات بصورة منفصلة ومنظمة، بدل وضع جميع وظائف الفحص في ملف واحد أو خلطها مع كود واجهة الـ API.

**ملاحظة مهمة:** في الأسبوع الأول كان التركيز على تأسيس الهيكل والواجهات المتفق عليها. لا يعني ذلك أن جميع الفحوصات الأمنية كانت قد اكتملت أو أصبحت جاهزة للاستخدام على مواقع حقيقية.

## 7. تحديد شكل نتائج الفحص والتقرير

تم وضع تصور موحد لنتيجة كل فحص حتى يستطيع الفريق عرض النتائج بطريقة مفهومة، وحتى لا تختلف صيغة النتائج من فحص إلى آخر.

تم اعتماد الحقول التالية لكل نتيجة:

| الحقل | وظيفته |
|---|---|
| `check_id` | معرّف الفحص |
| `title` | اسم الفحص |
| `status` | حالة الفحص |
| `severity` | درجة خطورة الملاحظة |
| `confidence` | مستوى الثقة في النتيجة |
| `evidence` | الدليل أو المعلومة التي تم رصدها |
| `explanation` | شرح النتيجة |
| `recommendation` | التوصية المقترحة |
| `limitations` | حدود الفحص وما لم يتم التحقق منه |

وتم التأكيد على ضرورة الفصل بين ثلاثة مفاهيم:

- **Status:** هل اجتاز الفحص أم ظهرت ملاحظة أم تعذر التحقق؟
- **Severity:** ما درجة خطورة المشكلة أو الملاحظة؟
- **Confidence:** ما مدى الثقة في النتيجة التي توصل إليها الفحص؟

كما تم اعتماد حالات النتائج التالية:

- `passed`: اجتاز الفحص المحدد.
- `warning`: توجد ملاحظة تحتاج إلى مراجعة.
- `not_verified`: لا يوجد دليل كافٍ للحكم.
- `error`: حدث خطأ أثناء تنفيذ الفحص.
- `skipped`: لم يتم تنفيذ الفحص.

كان الهدف من هذا التصميم منع التطبيق من إعطاء نتائج مضللة، مثل اعتبار الفحص الذي لم يتمكن من التحقق من النتيجة فحصًا ناجحًا.

## 8. وضع الأساس الأمني للمشروع

من أهم الأمور التي تم تحديدها في الأسبوع الأول أن CyberShield نفسه يجب أن يُبنى بطريقة آمنة؛ لأنه يتعامل مع عناوين مواقع يرسلها المستخدم إلى الخادم.

لذلك تم وضع مجموعة من المتطلبات الأمنية التي يجب أن يلتزم بها التنفيذ:

- فحص المواقع التي يملكها المستخدم أو لديه تصريح صريح بفحصها فقط.
- طلب تأكيد التفويض من المستخدم داخل التطبيق.
- التحقق من التفويض مرة أخرى داخل الخادم، وعدم الاعتماد على التطبيق وحده.
- عدم طلب كلمات مرور المواقع أو بيانات تسجيل الدخول.
- عدم تنفيذ محاولات تخمين كلمات المرور أو Brute Force.
- الاقتصار على طلبات HTTP محدودة وقرائية.
- إبقاء التحقق من شهادات TLS مفعّلًا.
- وضع حدود زمنية للطلبات.
- التعامل بحذر مع عناوين المواقع التي يدخلها المستخدم.
- منع استهداف العناوين الداخلية والخاصة والمحلية أو خدمات البيانات الوصفية السحابية.
- عدم كشف تفاصيل الأخطاء الداخلية للمستخدم.
- عدم وضع المفاتيح أو الأسرار داخل الكود أو Git.

هذه المتطلبات كانت أساسًا لخطة الحماية التي جرى تطويرها لاحقًا بصورة أكثر تفصيلًا.

## 9. تأسيس الاختبارات البرمجية

تم اعتماد `pytest` إطارًا لاختبار كود Python، وتجهيز أساس الاختبارات للتحقق من سلوك الـ API والماسح والنتائج.

كان الهدف من الاختبارات التأكد من أمور مثل:

- أن مسار Health يعمل بالشكل المتوقع.
- أن طلب الفحص يتعامل مع البيانات الصحيحة وغير الصحيحة.
- أن تأكيد التفويض يتم التحقق منه.
- أن نتائج الفحوصات ترجع بالصيغة المتفق عليها.
- أن حالات النجاح والتحذير وعدم التحقق والخطأ لا تختلط مع بعضها.

**الخلاصة:** كان الأسبوع الأول مرحلة تأسيس وتصميم وتنظيم وبناء الهيكل الأولي، مع إنشاء أساس للاختبارات وصل إلى 43 اختبارًا ناجحًا. أما التحسينات الأمنية الأعمق والتوسعات التي وصلت لاحقًا إلى 98 اختبارًا ناجحًا، فهي من إنجازات الأسبوع الثاني وليست من إنجازات الأسبوع الأول.
